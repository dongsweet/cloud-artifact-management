# 网闸对接模式调研与测试模拟器

## 调研结论

山石网科《安全隔离与信息交换系统（国产型号）用户手册 V2.0-G》描述了 FTP 同步、文件共享同步（SMB/NFS）、数据库同步、文件审核以及“新文件交换”等功能。手册明确支持 FTP/共享文件同步的外网到内网方向；同步策略可以选择周期、定时或时间段，并提供镜像、增量等模式。文件审核管理会列出被系统过滤的文件，审核通过后才允许接收；内网文件发送、接收和查杀病毒操作有独立审计日志。

手册没有提供 CAM 可直接调用的跨安全区 REST 业务 API，也没有说明“新文件交换”服务的外部调用协议、回执格式、分块续传能力或自动审核接口。网闸管理页面/设备管理 API 与跨区业务数据通道应视作不同能力，不能把设备管理 API 当作业务穿透接口。

## 建议采用的现场模式

根据现场确认，CAM 生产环境采用山石网闸的**映射模式**。映射模式是受控的 PNAT 访问：网闸将一侧的虚拟 IP/端口映射到另一侧指定服务器的指定 IP/端口，并按源对象、目的对象、协议和端口限制访问。它不是把两侧网络桥接起来，也不是开放任意 HTTP 穿透。

CAM 应为每条业务链路配置独立、最小化的映射规则。建议至少拆分为以下规则：

| 规则 | 方向 | 协议 | 映射目标 | 用途 |
|---|---|---|---|---|
| 审批申请 | 外部交换区 → 统一运维内网 | TCP | `cam-core` 的受控接收端口 | 送达审批申请消息 |
| 审批回执 | 统一运维内网 → 外部交换区 | TCP | `cam-edge` 的受控接收端口 | 返回审批状态和传输授权 |
| 正式制品传输 | 外部交换区 → 统一运维内网 | TCP | `cam-core` 的制品接收端口 | 传输已审批制品及清单 |
| 接收回执 | 统一运维内网 → 外部交换区 | TCP | `cam-edge` 的回执端口 | 返回完整性校验和入库结果 |

实际虚拟 IP、目标 IP、端口、入口设备和出口设备由网闸管理员根据现场地址规划填写，不能写死在 CAM 代码中。若现场将审批控制消息和大文件合并为一个 HTTPS 映射端口，应仍在应用层区分消息接口和制品接口，并分别校验权限、摘要和任务编号。

在映射模式下，CAM 的应用链路仍应保持异步和幂等：

1. 外部交换区通过映射地址向 `cam-core` 发起受控申请，申请消息带唯一 `requestId`、清单摘要和报告摘要。
2. `cam-core` 只接受网闸映射端口上的受控接口请求，不接受其他来源或其他端口；重复请求必须幂等处理。
3. 内网接收适配器检查清单、签名、摘要、目标安全域和云管审批状态，验证通过后才登记正式制品。
4. 内网通过反向映射端口回传状态和接收回执。审批结果以云管查询结果为准，网闸映射连接本身不能作为审批通过凭据。

网闸映射规则必须限制源对象、目的对象、协议、源/目的端口和入口/出口设备；禁止使用“所有协议”“所有地址”或整段端口范围。控制消息和大文件传输应使用不同端口或不同服务身份，便于审计和限流。映射规则变更由网闸管理员执行并留存审计记录，CAM 不直接修改设备策略。

生产部署仍需网闸管理员确认映射模式的虚拟 IP、映射端口、单向方向、连接超时、并发连接数、会话大小、审计日志和故障切换策略。手册未说明的单文件大小、自动续传和设备级限流行为不能视作已经具备；大文件仍由 CAM 自身负责分块、断点恢复和摘要校验。

## 测试环境文件摆渡模拟器

测试环境没有物理网闸时，可用 `tools/cam-gate-simulator.js` 模拟其**文件交付语义**。模拟器只允许两个明确的单向方向，每次以 `transferId` 传输一个不可变 bundle：

```text
<simulator-root>/
├─ outside/
│  ├─ outbox/<transferId>/manifest.json
│  ├─ outbox/<transferId>/content/...
│  └─ inbox/<transferId>/...
└─ inside/
   ├─ outbox/<transferId>/manifest.json
   ├─ outbox/<transferId>/content/...
   └─ inbox/<transferId>/...
```

清单含 schemaVersion、transferId、固定方向、分块大小、相对路径、文件大小、完整 SHA-256 和每块 SHA-256。模拟器拒绝目录穿越、符号链接、重复路径、方向错配、大小或摘要不一致；接收中断时保留 `.partial` 目录，重试时重新校验已有分块并跳过正确分块；完整文件校验通过后，以目录重命名原子发布，并写 `receipt.json`。同一 transferId 和同一清单可幂等重试，不同内容冲突。

运行示例：

```bash
node tools/cam-gate-simulator.js \
  --root /tmp/cam-gate-test \
  --direction outside-to-inside \
  --transfer-id TR-20261013-001
```

传输 bundle 的分块大小与清单声明绑定；首期测试按 256 MiB 分块。模拟器只负责测试文件在两个目录间的单向交付、断点恢复和回执，不负责冒充山石的审批审核界面、设备 API、恶意代码检测或安全隔离能力。它不会加入正式 Compose，也不得部署到生产安全区。

## 云管工单联调现状与启用条件

`cam-core` 已实现 EOMS 需求工单创建、详情查询、审批状态判定、待确认任务查询和确认关单的适配代码；本地测试覆盖请求构造和状态规则。代码存在不等于已对真实云管端到端验证，也不表示当前可从 Edge 页面提交。

测试机当前 `cam-core` 中，云管 API 基地址和服务身份已配置；但级别、来源、业务类型、所属中心、运维团队和处理人映射均未配置。只读字典请求尝试还遇到 socket 层错误，当前 VPN 网络路径也未验证成功。因而目前不能可靠创建工单。真实工单会写入云管业务系统，需等只读接口连通、映射检查通过后，由用户明确确认再做创建测试。

启用工单提交流程前还必须完成 Edge 审批申请与 Core 之间的文件消息交付、审批状态回传、正式制品传输和接收回执闭环。共享密钥应在该联动定型后实施版本化轮换：Core 生成新密钥，短期双密钥过渡，Edge 确认切换后撤销旧密钥；新旧密钥不写日志，轮换与撤销写审计记录。密钥如何通过隔离区安全分发须与网闸管理员共同定规，不能把明文密钥直接放入普通文件摆渡包。
